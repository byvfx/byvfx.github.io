Clippa

A pipeline that turns long livestreams into reviewed, captioned, scheduled YouTube videos and Shorts. It records, transcribes, finds the moments worth keeping, cuts them, writes titles and cover art, sends everything to a person for approval, and uploads on a schedule.

The problem

Hours of footage, a few minutes worth keeping

A live show runs four to ten hours, several nights a week. The good parts are scattered through it: a two-minute rant, a twenty-minute topic, a ten-second line that works as a Short. Finding and cutting them by hand takes longer than the show itself, and the channel needs a steady flow of uploads that read as if a person wrote them.

Clipper does the finding, cutting and packaging automatically and leaves one decision to people: whether each piece goes out. Every item arrives in review with its video, title, description, chapters and cover. A reviewer approves it, rejects it, or leaves a note, and a note triggers a re-cut.

Pipeline

Thirteen stages, each one command

Every stage is a clipper <stage> subcommand that reads and writes files in the stream's folder. The stages are idempotent, so clipper run resumes after a crash, skips finished work, and can redo from any stage with --from. One table in the code lists the stages, and the worker, the CLI and the web dashboard all read from it.

  1. record / fetch

    A Docker recorder on the NAS watches channels and captures each live show with its chat. Past broadcasts can be fetched instead.

    NAS
  2. transcribe

    WhisperX with word timings and speaker labels, on a cloud GPU. About $0.45 a stream.

    Modal L40S
  3. signals

    Chat rate and audio loudness over time: a heat map of where the audience reacted.

    Worker
  4. score

    Two passes. A fast model reads the whole transcript with the heat map; a stronger model judges only the shortlist.

    LLM
  5. segments

    Splits the stream into topics, and groups recurring topics across nights into compilations.

    LLM
  6. cut

    Lossless segment cuts on keyframes, re-encoded picks, and automatic bleeps for listed words in audio and captions.

    NAS ffmpeg
  7. meta

    Search-friendly title, description, chapters, tags and an .srt caption file, following a house style.

    LLM
  8. thumbs

    Cover art in each show's style. Faces are placed so they never sit under overlays.

    LLM + Pillow
  9. shorts

    Vertical 15–59 s versions. A vision model picks a layout for each scene and switches at every cut. Dead air between words is trimmed, but only where the audio is quiet too, so a laugh stays.

    Worker
  10. faces

    Who is on screen, with local CPU face detection and recognition (YuNet + SFace).

    Worker
  11. review

    Publishes everything to Kitsu, the review system of record, and posts cards with approve buttons to Discord.

    Kitsu · Discord
  12. schedule

    Fills daily slots by type, mixes shows, drops anything stale, and respects the per-day upload limit.

    Serve
  13. upload

    Private with a publish time, then playlists and source links. Runs every hour without anyone starting it.

    YouTube API

Outlined stages make up the fast lane: picks and Shorts reach review hours before the long segments are cut.

Architecture

One home NAS and a few cloud APIs

The work goes where it is cheapest. Everything that runs all the time lives on a home NAS in Docker, next to the footage: the recorder, the review tracker, and the services that run the pipeline, the war room and the bot. Video is cut and encoded there with the NAS's own Intel GPU, so hours of footage never cross the network. Only GPU transcription goes out, to Modal, billed by the second.

The config and all state sit in one folder on the NAS, so there is a single copy. Every service writes a heartbeat file, and the war room reaches a phone over Tailscale. No other computer has to be on. The same services can also run on a Windows machine as scheduled tasks, and the old laptop setup is kept, switched off, as a rollback.

A new machine is set up by role: GPU worker, serve, bot, recorder, Claude, or a control station that runs nothing unattended. clipper setup writes that machine's config, and clipper doctor --role … checks exactly what that role needs. A Mac on Apple Silicon is set up as a control station.

Review

Nothing goes out until a person says so

Kitsu holds every decision, with one production per show and one episode per stream. The Discord bot mirrors each item as a card with buttons, so a reviewer can approve from a phone. The war room is the full review desk. All three act through the same code path, so a click in one place shows up in the other two.

ArrivesVideo, title, description, chapters, coverin Kitsu, as a Discord card, and in the war room queue
DecideApprove · reject · hold · notefrom any of the three, with undo
A noteBecomes a retakere-cut, re-trimmed or redrawn automatically, then back to review
ApprovedScheduled and uploadedthe next free slot on YouTube, and on X while the topic is hot

Guardrails before review

Some items arrive already flagged. A Short with more than five seconds of voices that aren't the show's own (usually a video playing on stream) is held, and its card shows the seconds counted from the speaker labels. The reviewer releases it when the show's commentary carries the moment.

The bot sends a DM when something needs a person: a stream ready for review, a failed upload, a stage that failed after its retries, recorder trouble, a filling disk. Quiet hours hold these until morning, and a daily digest arrives at 09:00.

The war room

A web page served by the always-on service, and installable on a phone over Tailscale. It shows what is live and whether it is recording, where each stream is in the pipeline, the review queue and the upload schedule, plus panels for GPU jobs, costs and analytics.

It also opens the cast library, the news stories and the research dossiers, so all of the tools above have one place to work from.

A usability pass made it safe to use quickly: a bulk approve touches only the items on screen (approved items upload on their own), a double tap sends once, and the header turns amber, then red, when its data goes stale.

Distribution · X

Shorts on X, built around how X bills

Approved Shorts go to X through the API as native video. Posting runs every hour and takes the newest streams from the last 72 hours first, up to six posts a day. It doesn't wait for YouTube, because a clip is worth most on X while the topic is still being talked about.

X charges about $0.015 for a post and $0.20 for a post with a link, so Clipper never includes a link. The post text leads with the hook, since the feed shows only the first words. It then adds up to three hashtags and a credit line that tags whose footage it is. Tall videos are re-encoded to X's recommended 720×1280. The weekly issue goes out as a thread, four pages per post, and a thread that fails halfway picks up as replies to the last post. Each post's cost is logged with the model calls.

Design decisions

What makes it hold up unattended

People decide, in one place

Every review action, whether a Discord button, a dashboard click or a Kitsu status, goes through one module and lands in Kitsu. There is no second database to fall out of sync.

A note on an item ("start two seconds later", "wrong face on the cover") becomes an automatic retake: Clipper re-cuts or redraws that item and sends it back for review.

Spend money only where it changes the answer

A cheap model reads everything and a strong model judges the shortlist. Paid stages refuse to rerun without --force. Cut keeps picks whose in and out points haven't changed, and covers are kept while their cut is unchanged.

Every paid stage takes --dry-run, which builds the prompts it would send and prints the estimated cost without calling anything. Every model call is logged with its token counts and price. clipper costs and the dashboard break spend down by stage, stream and provider.

Models and prompts are swappable and versioned

All model calls go through one layer, and the provider comes from the model string's prefix (Claude, OpenAI, Gemini, OpenRouter or local). Prompts are versioned files. A version that produced reviewed output is never edited; changes go into a new version.

clipper compare runs candidate models against a gold set of past reviewer decisions before a stage switches models.

One install, many shows

Config is layered: code defaults, a shared file, this machine's own file, then environment variables. Each show gets its own table with cast, style, budgets and layouts, and a single stream can override anything.

Adding a show is a config table and a Kitsu production, with no code changes. clipper doctor checks every dependency, key and service and prints the fix for each failure. clipper setup writes a new machine's config.

State that survives crashes

JSON state is written to a temp file, then swapped in. Updates take a lock, and readers retry when they catch a file mid-replace. Library code raises one error type with a one-line message, and only the CLI turns it into an exit.

Tests enforce the conventions: a test fails on a raw JSON read or a stray SystemExit, on a broken docs link, or on a CLI command missing from its group.

A schedule that stays current

Uploads fill fixed daily slots by type (Shorts, segments, compilations), alternate between shows, and stay under the channel's daily limit. Approved items older than a few days drop out, so the channel never falls weeks behind the shows.

The first version queued everything, and the newest stream ended up 15 days behind. Switching to "stay current" was a product decision, made from the data.

Measure before switching models

clipper compare runs a candidate model or prompt on streams that people have already reviewed, and counts how many of the approved moments it finds and how many windows it keeps. Running the same prompt twice first sets a noise floor, so a change is adopted only when it beats that.

Twelve models were tried through OpenRouter, with reasoning on and off. A newer restructured prompt found 8 of 18 approved moments against 6 for the previous one, but the gap is within the noise, so it stays a candidate. Every trial and its cost is written up on a wiki page.

It checks on itself

clipper checkup reads only the files the services write: stale heartbeats, a stage stuck for hours, a recording nobody picked up, an upload late for its slot, a title over YouTube's limits. clipper status puts services, streams, review counts, the next releases and the month's spend on one screen.

A nightly report is built on top of it. When nothing is wrong it sends a one-line DM with no model call. When something is wrong, Claude Code runs headless with read-only tools and sends one DM with its diagnosis. If that fails, the raw findings go out instead. A weekly digest covers runs, uploads, spend and review decisions, and once a month a read-only Claude pass reads those weeks to find the problems that keep coming back.

A bug worth telling

The compilation that repeated itself

A reviewer noticed a speaker "repeating himself" two hours into a compilation. Lossless cuts have to start on a keyframe, so each segment file began up to five seconds before its real start. Joined back to back, every join replayed the tail of the previous part: 13 of 15 joins in that video.

The fix ends each part with a concat outpoint exactly where the next file begins. The cuts stay lossless and the joins are now frame-accurate. A regression test covers it.

Research and context

Tools that know who is on screen and what is going on

Clips are only as good as the context behind them. Four tools around the pipeline track the people in the shows, the news about them, and the stories the shows cover. They follow one rule: a model can find, sort and summarize, but every claim it makes has to point back to a real source. That means a quote that appears word for word in a transcript, a headline with its link, or a search result the code actually fetched. Output that can't be traced back is rejected.

Shared engine · search swarm

Many small searches that follow their own leads

A planner model turns a goal (a story brief or a lead) into up to 16 first searches. Cheaper worker models run eight at a time, each using one tool: YouTube, Kick or Odysee channels, Reddit and the web, past transcripts, or Clipper's own segments. Each worker marks the results that fit and suggests up to three follow-ups. A coordinator merges duplicates, queues the new follow-ups, and stops at a round, task, budget or time limit. The whole task tree is saved so a run can resume.

A model never fetches anything directly. A finding has to be one of the tool's own results, a follow-up has to parse as a valid query or channel, and any search for a person's whereabouts or private details is dropped. In one 30-task run it found 109 results (44 strong) across five platforms for about $0.03.

Cast library

clipper cast

Keeps a set of head-and-shoulders photos of each regular for cover art. Photos come from the streams themselves, Wikimedia Commons, the person's own channels and image search. It fills itself: each new stream adds the sharpest frames of anyone still short of photos, and a daily job searches the other sources.

Each photo has to match the person's enrolled face before it is kept, then gets a 4:5 crop and an expression label ("neutral", "laughing", "angry") for about $0.0002. Photos are kept automatically only from sources with a known origin, never from image search or photo agencies. Covers pick the photo whose expression fits the story.

News watcher

clipper news

Watches headlines for the names you give it and posts new stories to Discord. One button adds a story to the context for the show's next stream, so scoring knows what the audience already knows. An hour before a show usually starts, it suggests that day's stories.

A cheap model checks each headline: is it really about this person and not someone with the same name, is it new, and is it about public conduct. Stories about private people or anyone's children are never posted. Five outlets on one event become one story. Only headlines and links are stored, never the articles. A check costs well under a cent.

Investigations

clipper investigate

Reads a public figure's own back catalog and comes back with leads: claims that changed over time, numbers that moved, things promised and never delivered, topics that suddenly took over. Then it checks whether anyone else has covered each lead.

A model pulls checkable statements from each video, and a statement is kept only if its quote is in the transcript with the numbers and any "not" unchanged. Patterns are found in code with no model call, and a stronger model writes up or rejects each one. Rejections are kept with the reason. Every receipt links to the exact moment. Leads are research for a person, never posted automatically. A full multi-year catalog costs about $14, and later runs read only new uploads.

Story dossiers

clipper story

Give it a one-line brief and a time window. The search swarm finds the videos, triage picks which ones are worth transcribing within an hour budget, and the result is a research dossier: summary, timeline, who said what, conflicts, gaps and angles. From there it plans an edit with chapters, lower thirds and every source credited, ready for review or as a narrated catch-up to watch yourself.

The timeline marks each event as shown, reported or speculation. Every line cites a moment or a source. A citation that doesn't resolve is sent back once, and if it still doesn't resolve, the step fails. When a re-upload repeats an earlier part, the duplicate is dropped from the edit.

  • Archive search. Thousands of hours of a back catalog transcribed in bulk on Modal and indexed with SQLite full-text search, so you can ask questions across years of video.
  • Weekly issue. A ten-page magazine of the week's stories, laid out and rendered automatically for social carousels.
  • Narrated pieces. Scripts read by an ElevenLabs voice, cut together with source clips, and finished in DaVinci Resolve through its scripting API.

How it was built

One person, with an AI pair programmer

I designed the system and made the product calls: what gets automated, where a person stays in the loop, what each stage may spend, and how the schedule behaves. I built it with Claude Code as a pair programmer. The project's conventions are written down in the repo, and every pull request gets an automated code review that has to be answered before merge. Copilot reviews first. When its quota runs out, the review falls back to Grok through OpenRouter, for about $1 a PR. I picked Grok after 13 models reviewed the same real PR: three of them made the same false claim about an ffmpeg filter, which a test disproved. Dependabot keeps the dependencies current.

About 36,000 lines across 110 modules and some 650 commits in under four weeks, running every day since the first week.

Once it was running, I audited the code as if handing it to another team and worked through the findings in tiers:

  • Broke five import cycles.
  • Split the war room into a package.
  • Moved prompt versions into one registry that the stages, doctor and a test all read.
  • Moved the defaults into a single file.
  • Shipped the prompts inside the package.
  • Added CI on Windows alongside Linux.
  • Added tests where the risk was.
